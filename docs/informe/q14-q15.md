# Consultas 14 y 15 — Registro de una venta y descuento de stock

**Enunciado 14:** registro de una nueva venta "Completada" (cabecera e ítems) con validación de: cliente existente y activo; farmacéutico existente, activo y de una sucursal tipo "Farmacia"; productos existentes y activos; y, para productos bajo receta, receta existente, vigente y del mismo cliente. El total se calcula a partir de los ítems y se actualiza la receta según las reglas de negocio.

**Enunciado 15:** actualización masiva del stock: dada una venta registrada, decrementar las unidades de cada producto del detalle en los lotes de la sucursal del farmacéutico, aplicando FEFO y omitiendo lotes vencidos. Si el stock vigente no alcanza para algún ítem, la operación completa se rechaza sin modificar ningún lote.

**Integración:** si el descuento de stock falla, no deben quedar una venta ni una receta modificadas. (Consigna, pp. 6–7)

**Motores:** MongoDB (clientes, farmacéuticos, sucursales, productos, recetas, ventas y contadores) y Redis (stock por lote).

**Código:**

| Función | Parámetros | Retorno |
|---|---|---|
| `q14.ejecutar(id_cliente, id_farmaceutico, items, medio_pago, id_receta=None, hoy=None)` | `items`: lista de `(id_producto, cantidad)`. `hoy`: fecha de la venta; por defecto, la del sistema. | `venta` (documento insertado), `receta` (`antes` y `despues`, o `None`) y `stock` (resultado de q15). |
| `q15.ejecutar(id_venta, hoy=None, sesion=None)` | `sesion`: la sesión de MongoDB de q14, si se llama desde ahí. | `id_venta`, `id_sucursal` y `lotes`: cada lote tocado con unidades `antes`, `descontadas` y `despues`. |
| `stock.descontar(...)` y `stock.reponer(id_venta)` | Scripts Lua de `farmared/stock.py`. | Lotes descontados; cantidad de lotes repuestos. |

Las dos consultas lanzan `ErrorDeValidacion` sin modificar nada si el pedido viola una regla.

## Decisiones

### Estrategia de consistencia

Las dos consultas tocan dos motores, y **no existe una transacción que abarque MongoDB y Redis**. Usamos lo que garantiza cada uno:

| Motor | Garantía que usamos |
|---|---|
| MongoDB | Transacción de varios documentos: la venta y la receta se confirman o se descartan juntas. *Complemento (no está en las clases): requiere replica set; por eso el compose levanta un replica set de un nodo.* |
| Redis | Un script Lua se ejecuta de forma atómica: ningún otro cliente es atendido mientras corre (Clase 17, p. 31). |

El todo o nada entre los dos motores sale del **orden de las operaciones**, con compensación solo para la última falla posible:

1. **MongoDB:** abre una transacción. Dentro de ella valida, inserta la venta y actualiza la receta, **sin confirmar**.
2. **Redis:** q15 ejecuta el script `descontar`. O descuenta todos los productos, o no toca ningún lote.
3. **Si Redis rechaza** (stock insuficiente) o algo falla antes: se aborta la transacción. No queda nada escrito y no hay nada que compensar.
4. **Si Redis descuenta:** se confirma la transacción.
5. **Si la confirmación falla:** se mira si la venta quedó registrada, porque una confirmación con resultado incierto puede haberse aplicado. Si no quedó, se compensa con el script `reponer`, que devuelve a cada lote lo que se le descontó.

| Dónde falla | Venta y receta | Stock |
|---|---|---|
| Validación (paso 1) | Transacción abortada | Sin tocar |
| Stock insuficiente (paso 2) | Transacción abortada | Sin tocar: el script verifica todos los productos antes de escribir |
| Error después del Lua, antes de confirmar | Transacción abortada | Repuesto con `reponer` |
| Confirmación rechazada | No registradas | Repuesto con `reponer` |
| Confirmación aplicada con error de red | Registradas | Descontado (correcto) |

**Por qué Redis va segundo:** el rechazo más frecuente es la falta de stock. Con este orden se resuelve abortando la transacción de MongoDB, sin compensar. Si Redis fuera primero, cada rechazo de una validación de MongoDB obligaría a devolver stock.

**Por qué un script Lua y no `MULTI`:** `MULTI` encola comandos sin poder decidir según lo que lee, así que no puede comprobar que alcance el stock antes de descontar, y no tiene rollback (Clase 17, p. 12; Clase 18, p. 7). El script arma el plan FEFO de todos los productos en una primera pasada y escribe solo si alcanzan todos. Como Redis no atiende a otro cliente en el medio, dos ventas simultáneas no pueden ver el mismo stock.

**Por qué no `with_transaction` de pymongo:** ante un error transitorio vuelve a ejecutar toda la función, y con ella el descuento en Redis. q14 maneja la transacción a mano y reintenta solo el paso 1, que es anterior al Lua.

### Cómo se conectan q14 y q15

La consigna presenta a q15 como un servicio propio que parte de "una venta registrada". Por eso q15 recibe el **id de la venta** y la lee de MongoDB. q14 le pasa su sesión: dentro de la transacción, q15 ve la venta recién insertada aunque todavía no esté confirmada. La misma función sirve integrada en q14 y sola, desde la terminal.

### Una venta no se descuenta dos veces

En la misma operación atómica en que descuenta, el script registra la venta:

| Clave | Tipo | Contenido |
|---|---|---|
| `ventas:descontadas` | Set | Ventas cuyo stock ya se descontó. El script rechaza una venta que ya está. |
| `descuento:{id_venta}` | Hash | `id_lote` → unidades que se descontaron de ese lote para la venta. |

- Los lotes de los CSV ya reflejan las ventas históricas, así que la carga marca como descontadas las ventas "Completada" de los CSV. Sin eso, `q15 V003` descontaría de nuevo.
- `descuento:{id_venta}` le dice a la compensación exactamente qué devolver.
- La marca y el descuento se escriben juntos: no puede quedar uno sin el otro.

### Reglas de negocio y supuestos

| Tema | Decisión | Fundamento |
|---|---|---|
| Producto "Bajo receta archivada" | Exige una receta de tipo "Archivada". | Supuesto nuestro: la consigna no lo dice, pero los datos son coherentes (V009 vende PRD008 con RC005, que es Archivada). |
| Venta con productos de venta libre y bajo receta | Se permite. La venta es "Con receta" si algún producto la exige; si no, "Venta libre". El tipo se deriva, no se recibe. | La receta cubre los productos que la necesitan; los de venta libre no la requieren. |
| Receta informada sin producto que la exija | Se rechaza. | Consumiría una dispensa sin motivo. |
| Unidad de dispensa | Una venta es una dispensa, aunque tenga varios productos bajo receta. | Así vienen los datos: `dispensas_realizadas` coincide con las ventas "Completada" de cada receta. |
| Próxima dispensa | Fecha de la venta + 30 días. Al llegar a las autorizadas, "Completada" y `proxima_dispensa` vacía. | Regla de la consigna (p. 5). RC002 no la cumple en los datos provistos (tiene 31 días); se carga como viene. |
| Dispensa adelantada | No se bloquea una receta prolongada cuya próxima dispensa todavía no llegó. | La consigna enumera las validaciones de q14 y esta no está. Ver [Limitaciones](#limitaciones). |
| Precio | El de lista vigente al vender; no se recibe como parámetro. El total es la suma de cantidad × precio. | Regla de precios (consigna, p. 5). |
| Fecha de la venta | Hoy (fecha del sistema), con `hoy` opcional para pruebas. | Consigna, p. 6. |
| Sucursal de la venta | La del farmacéutico, copiada en `ventas.id_sucursal`. q15 descuenta de esa sucursal. | Consigna, p. 6. |
| Lote vencido | `vencimiento < hoy`: un lote se dispensa hasta el día de su vencimiento inclusive. | Convención de `docs/modelo.md`. |
| Producto repetido en dos ítems | Se acepta; q15 suma las cantidades por producto antes de calcular FEFO. | Si no se sumaran, cada ítem vería el mismo stock. |
| Validaciones extra | Cantidad entera mayor a 0; medio de pago entre los del CSV; "Obra social" solo para clientes con cobertura. | Evitan ventas sin sentido; no están en la consigna. |

### Ids de la venta y de sus ítems

Los ids siguen la serie del CSV (`V017`, `D023`…). Salen de la colección `contadores`, que la carga inicializa con el último id de cada serie, con un `$inc` atómico **fuera** de la transacción. Calcular el máximo + 1 dentro de la transacción hacía que las ventas simultáneas eligieran el mismo id y chocaran una y otra vez: con 25 ventas a la vez se agotaban los reintentos. Con el contador, ninguna compite por el id. A cambio, una venta rechazada por stock deja su número sin usar, igual que una secuencia de una base relacional. Un índice único sobre `ventas.items.id_detalle` protege la unicidad de los ítems.

### Concurrencia

- **Stock:** el script Lua es atómico, así que dos ventas simultáneas no pueden descontar las mismas unidades ni dejar un lote en negativo.
- **Receta:** la actualización filtra por `estado: "Vigente"` y por las `dispensas_realizadas` leídas. Si dos ventas usan la misma receta a la vez, MongoDB aborta una por conflicto de escritura y q14 la reintenta desde cero. Al volver a validar, la receta ya refleja la otra venta.

## Pruebas de consistencia

Las fallas de infraestructura no se pueden provocar desde la terminal, así que las simulamos en Python reemplazando una función. Después de cada caso comparamos el estado completo (ventas, receta, unidades de todos los lotes y claves `descuento:*`) con el de antes:

| Caso | Resultado |
|---|---|
| La confirmación de MongoDB falla después del Lua | Sin venta ni cambio en la receta; todos los lotes con sus unidades de antes. |
| La confirmación se aplica pero la respuesta se pierde | Venta registrada y stock descontado; no se compensa. |
| Falla entre el Lua y la confirmación | Transacción abortada y stock repuesto. |
| 8 ventas simultáneas sobre la última dispensa de RC002 | Se registra una; las otras 7 se rechazan con "la receta RC002 no está vigente (Completada)". |
| 25 ventas simultáneas de 10 unidades sobre un lote de 200 | Se registran 20, el lote queda en 0 y nunca en negativo; los 20 ids de venta y los 42 ids de ítem son únicos. |

## Limitaciones

- **Caída del proceso entre el Lua y la confirmación.** Si el proceso muere justo ahí, el stock queda descontado sin venta. El descuento queda registrado en `descuento:{id_venta}`, así que se detecta comparando `ventas:descontadas` con las ventas de MongoDB y se devuelve con `stock.reponer(id_venta)`. No lo automatizamos.
- **Dispensa adelantada.** No validamos que una receta prolongada respete su próxima dispensa, porque la consigna no lo pide.
- **La receta no indica qué productos cubre.** Solo validamos que exista, sea del cliente, esté vigente y, para productos archivados, que sea archivada.
- **Precio de lista.** No modelamos descuentos de obra social: el precio del ítem es el de lista.
- *Complemento (no está en las clases):* el script Lua lee los hashes `lote:{id}` sin declararlos como claves del script. Funciona en un Redis de un solo nodo, como el nuestro. En Redis Cluster habría que ubicar las claves de una sucursal en el mismo nodo con *hash tags*.
